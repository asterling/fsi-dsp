# CFK on OpenShift -- Confluent for Kubernetes Scenario

Self-contained Helm values and CRD manifests for deploying a fully governed Kafka environment on OpenShift using the Confluent for Kubernetes (CFK) operator.

## Prerequisites

- OpenShift 4.14-4.21 (OCP cluster with cluster-admin access)
- Helm 3.x
- cert-manager 1.x (most OpenShift clusters include this; see [cert-manager docs](https://cert-manager.io/docs/installation/))
- kubectl or oc CLI
- Confluent for Kubernetes operator (see Installation below)

## Installation

Two paths for installing the CFK operator, depending on your environment:

### Path 1: OLM (OperatorHub) -- Standard OpenShift

Install directly from the OpenShift OperatorHub UI:

1. Navigate to **Operators > OperatorHub** in the OpenShift console
2. Search for **Confluent for Kubernetes**
3. Click **Install**, select the `confluent` namespace
4. Wait for the operator pod to become Ready

> **Note:** Configuration options are limited when installed via OperatorHub.
> For production deployments requiring custom configuration, use the Helm path below.

### Path 2: Helm Chart -- Air-gapped / Full Customization

```bash
helm repo add confluentinc https://packages.confluent.io/helm
helm repo update
helm upgrade --install confluent-operator \
  confluentinc/confluent-for-kubernetes \
  --namespace confluent --create-namespace
```

This path provides full control over operator configuration and is recommended for production environments.

## Quick Start

### 1. Install the CFK operator

Use either OLM or Helm path above.

### 2. Apply Kafka, Schema Registry, and Connect CRs

```bash
oc apply -f values/kafka-rest-class.yaml
oc apply -f values/kafka.yaml
oc apply -f values/schemaregistry.yaml
oc apply -f values/connect.yaml
oc apply -f values/connect-mm2.yaml
```

Wait for all pods to become Ready:

```bash
oc get pods -n confluent -w
```

### 3. Apply KafkaTopic CRDs

```bash
oc apply -f topics/
```

### 4. Apply ACLs

```bash
# Review and adapt ACL templates for your principals
oc apply -f acls/acl-templates.yaml
```

## Authentication

This scenario uses **mTLS** (mutual TLS) for Kafka broker authentication, managed by CFK with cert-manager integration:

- `tls.autoGeneratedCerts: true` enables CFK to auto-generate and rotate certificates
- cert-manager handles the TLS certificate lifecycle
- Principal mapping extracts the CN from the client certificate for identity

All inter-component communication (SR to Kafka, Connect to Kafka) uses internal mTLS listeners.

## Authorization

### Default: Kafka ACLs (Simple)

The default authorization mode is `simple` (Kafka ACLs). This requires no external infrastructure and maps to the same producer=DeveloperWrite / consumer=DeveloperRead patterns used in Confluent Cloud scenarios.

See `acls/acl-templates.yaml` for reference ACL definitions.

### Advanced: MDS (Confluent RBAC)

For teams needing CC-equivalent role bindings with centralized identity management, MDS provides Confluent RBAC. This requires LDAP/AD backend infrastructure and the MDS service.

See `acls/acl-mds-alternative.yaml` for MDS configuration reference.

## Flink Kubernetes Operator

Flink Kubernetes Operator 1.14.0 is bundled in this scenario (per D-09) for stream processing parity with CC Flink. Single scenario = complete platform (Kafka + SR + Connect + MM2 + Flink).

### Prerequisites

- Flink Kubernetes Operator Helm chart (see installation below)
- Custom Flink Docker image with Avro-Confluent connector JARs (see below)

### Installation

```bash
helm repo add flink-operator \
  https://archive.apache.org/dist/flink/flink-kubernetes-operator-1.14.0/
helm install flink-kubernetes-operator \
  flink-operator/flink-kubernetes-operator \
  --namespace flink --create-namespace \
  -f flink/flink-operator-values.yaml
```

### Custom Docker Image

The base Flink image does not include the avro-confluent format connector JARs. Build the custom image before deploying FlinkDeployment CRDs:

```bash
docker build -t fsi-flink:1.20 flink/flink-docker/
```

> **Air-gapped environments:** Download the connector JARs locally and modify the Dockerfile to use `COPY` instead of `wget`. See comments in `flink/flink-docker/Dockerfile`.

### Deploy Examples

```bash
kubectl apply -f flink/flink-session-cluster.yaml -n flink
kubectl apply -f flink/examples/tumbling-window.yaml -n flink
kubectl apply -f flink/examples/stream-table-join.yaml -n flink
kubectl apply -f flink/examples/filter-and-route.yaml -n flink
```

### CC Flink to CFK Flink Template Mapping

CC Flink auto-discovers SR subjects. CFK Flink requires explicit CREATE TABLE statements with avro-confluent format connector. See Pitfall 5 in research.

| CC Flink Template | CFK FlinkDeployment | Key Difference |
|-------------------|---------------------|----------------|
| tumbling-window-aggregation.sql | flink/examples/tumbling-window.yaml | Explicit CREATE TABLE with avro-confluent format |
| stream-table-join-enrichment.sql | flink/examples/stream-table-join.yaml | Temporal table source requires explicit table definition |
| filter-and-route.sql | flink/examples/filter-and-route.yaml | EXECUTE STATEMENT SET preserved, tables defined explicitly |

## Observability

### Kafka JMX Metrics

CFK exposes metrics on port 7778 (Prometheus JMX exporter). PodMonitor in `observability/pod-monitor-kafka.yaml` scrapes these. The Kafka CR in `values/kafka.yaml` includes matching Prometheus rules in `spec.metrics.prometheus.rules`.

### Flink Metrics

Flink uses built-in PrometheusReporterFactory on port 9249. PodMonitor in `observability/pod-monitor-flink.yaml` scrapes these. JMX exporter sidecar config (`observability/jmx-exporter-flink.yaml`) is mounted in FlinkDeployment CRDs via podTemplate volumeMount (per D-11).

### Dashboard Templates

Import dashboards from `observability/{provider}/` directories. CFK/CP metrics use JMX exporter stubs from Phase 5. See the main platform `observability/` directory for provider-specific dashboards (Grafana, Dynatrace, Datadog, Splunk, New Relic, Instana).

## CFK Topic Reconciliation

**Important:** All topic changes must go through KafkaTopic CRDs (GitOps workflow). The CFK operator continuously reconciles KafkaTopic CRDs against the actual Kafka topic state. Manual topic changes made via CLI or Control Center will be **reverted** by the reconciliation loop.

## Cloud-Specific Notes

- **OpenShift SCC:** CFK 3.2 supports OpenShift 4.14-4.21. If pods fail to start with permission errors, verify SecurityContextConstraints allow the required security context.
- **Networking:** Configure OpenShift Routes or LoadBalancer services for external Kafka access.
- **cert-manager:** Must be installed cluster-wide before deploying CFK components with auto-generated certs.
- **DR regions:** Configure source cluster endpoints in MM2 connector CRDs for cross-cluster replication.
