**`scenarios/cc-azure/oauth.tf`:**
```hcl
# =============================================================================
# OAuth/OAUTHBEARER — Azure AD (Entra ID) Identity Provider
# =============================================================================
# Implements ADR-006: OAuth as primary auth for CC on Azure.
# Teams configure their Azure AD tenant and app registration, then
# producers/consumers authenticate via OAUTHBEARER tokens.
#
# Prerequisites:
#   1. Azure AD app registration with API permissions for Confluent Cloud
#   2. Azure AD group(s) for Kafka producers and consumers
#   3. var.azure_tenant_id set in terraform.tfvars
# =============================================================================

resource "confluent_identity_provider" "azure_ad" {
  display_name = "Azure AD (Entra ID)"
  description  = "FSI Azure AD identity provider for OAUTHBEARER authentication"
  issuer       = "https://login.microsoftonline.com/${var.azure_tenant_id}/v2.0"
  jwks_uri     = "https://login.microsoftonline.com/${var.azure_tenant_id}/discovery/v2.0/keys"
}

resource "confluent_identity_pool" "producers" {
  identity_provider {
    id = confluent_identity_provider.azure_ad.id
  }
  display_name   = "Kafka Producers"
  description    = "Identity pool for Azure AD authenticated Kafka producers"
  identity_claim = "sub"
  filter         = "claims.aud==\"${var.confluent_cloud_app_id}\" && claims.groups.exists(g, g==\"${var.azure_producer_group_id}\")"
}

resource "confluent_identity_pool" "consumers" {
  identity_provider {
    id = confluent_identity_provider.azure_ad.id
  }
  display_name   = "Kafka Consumers"
  description    = "Identity pool for Azure AD authenticated Kafka consumers"
  identity_claim = "sub"
  filter         = "claims.aud==\"${var.confluent_cloud_app_id}\" && claims.groups.exists(g, g==\"${var.azure_consumer_group_id}\")"
}
```

**`docs/rotation-runbook.md`:**
Create a credential rotation runbook with these sections:

1. **Overview** -- Why rotation matters for FSI (90-day max per policy, zero-downtime requirement)
2. **Vault Golden Path (Recommended)** (per D-04, D-07):
   - Vault KV v2 path convention: `secret/fsi-kafka/{env}/{domain}/{sa-name}` (per D-06)
   - Reference Terraform pattern: `vault_kv_secret_v2` resource with `max_versions = 2`
   - Step-by-step rotation procedure (per D-05):
     1. Create new API key via `confluent api-key create` for the service account
     2. Write new credential to Vault at the prescriptive path (new version)
     3. Both credentials now active (dual-credential window begins)
     4. Deploy applications with new credential (rolling restart or config reload)
     5. Wait for configurable window (default 24h per D-05) -- monitor for auth failures
     6. Revoke old API key via `confluent api-key delete`
     7. Verify: no auth failures in monitoring after revocation
   - Vault TTL configuration for automatic window enforcement
   - Example Vault CLI commands for each step
3. **Cloud-Native Alternatives** (per D-07 -- documented, not full Terraform):
   - **Azure Key Vault**: Store API keys in Key Vault secrets, use managed identity for access, rotation via Azure Automation runbook. Link to Azure Key Vault rotation docs.
   - **AWS Secrets Manager**: Store API keys in Secrets Manager, use IAM roles for access, rotation via Lambda function. Link to AWS rotation docs.
   - **GCP Secret Manager**: Store API keys in Secret Manager, use service account for access, rotation via Cloud Functions. Link to GCP rotation docs.
4. **OAuth Token Rotation** -- Explain that OAuth tokens auto-rotate via IdP (1-hour lifetime recommended). No manual rotation needed for OAUTHBEARER. Reference ADR-006.
5. **Terraform Provider Credentials** -- API keys only (provider does not support OAuth). Store in CI secrets. Rotate quarterly. Reference ADR-006.
6. **Emergency Rotation** -- Compromised credential procedure: revoke immediately (accept brief downtime), create new key, deploy, verify.

**`docs/csfle-guide.md`:**
Create a CSFLE setup guide with these sections:

1. **Overview** -- What CSFLE is, why FSI needs field-level encryption for PII, how it works (envelope encryption: KEK wraps DEK, DEK encrypts fields tagged PII)
2. **Prerequisites** -- Stream Governance Advanced package required on CC environment (per research pitfall #2). KMS access configured.
3. **KMS Provider Setup** (per D-08):
   - **AWS KMS**: Key policy granting Confluent Cloud access, ARN format: `arn:aws:kms:us-east-1:123456789012:key/...`
   - **Azure Key Vault**: Access policy for Confluent Cloud service principal, Key Identifier URI format: `https://my-keyvault.vault.azure.net/keys/my-key/...`
   - **GCP Cloud KMS**: IAM binding for Confluent Cloud service account, Resource name format: `projects/my-project/locations/.../cryptoKeys/my-key`
   - **HashiCorp Vault Transit**: Transit engine configuration for Confluent CSFLE
4. **Terraform Configuration** -- How the topic module's CSFLE works:
   - Set `data_classification = "confidential"` and populate `pii_fields`
   - Module creates KEK registration and schema encryption rules automatically
   - Provide `kek_name`, `csfle_kms_type`, `csfle_kms_key_id` variables
   - Example module call with confidential topic
5. **Client Configuration** -- OAUTHBEARER + CSFLE client properties for Java and .NET showing the `rule.executors` and `rule.actions` properties needed for CSFLE
6. **Validation** -- How to verify CSFLE is working: produce a message, consume raw (encrypted), consume with authorized consumer (decrypted)
7. **Troubleshooting** -- Common issues: "encryption rules not supported" (missing Advanced package), KMS permission errors, empty ruleset block error
